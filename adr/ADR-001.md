# ADR-001 — Proveedor de datos de fútbol

- **Estado:** Aceptado  *(ratificado por el propietario, 2026-07-27)*
- **Fecha:** 2026-07-27
- **Decisores:** CTO (propuesta) · Propietario del proyecto (ratifica)
- **Fase:** 0 (Investigación)

## Contexto

El proyecto necesita datos de fútbol para múltiples ligas: jugadores, entrenadores,
lesiones, sanciones, alineaciones, sustituciones, resultados, eventos, calendario,
estadísticas y cambios de entrenador (ver [`../docs/00_VISION.md`](../docs/00_VISION.md) §7).

Restricciones de la visión y de [`../CLAUDE.md`](../CLAUDE.md):
- **Nunca dependemos directamente de una API externa**: todo se sincroniza a nuestra BD
  propia con **IDs internos**, tras un **adaptador anticorrupción** (patrón *Football Data
  Hub*). Debe poderse **cambiar de proveedor sin tocar el resto del sistema**.
- **Presupuesto de desarrollo: €0** (solo Railway, ya disponible). El gasto en API de pago
  se difiere hasta el lanzamiento al mercado.
- Los **entrenadores** son un pilar diferencial → el proveedor **debe** dar datos de
  entrenador.

Investigación de respaldo: [`../research/APIs.md`](../research/APIs.md),
[`../research/Costs.md`](../research/Costs.md), [`../research/Legal.md`](../research/Legal.md)
(investigado 2026-07-27).

## Opciones consideradas

### Opción A — API-Football (api-sports.io)
- **Ventajas:** todas las competiciones en cualquier plan de pago (1.236 ligas); cubre todo
  lo necesario incl. **entrenadores**, lesiones, alineaciones, subs, eventos (~15s), stats,
  traspasos; **el precio no escala por nº de ligas**; arranque **$19/mes**; buena doc.
- **Inconvenientes:** calidad algo inferior a premium; sin xG en tiers básicos; empresa
  no-UE (revisar ToS comercial/redistribución).

### Opción B — SportMonks
- **Ventajas:** mayor cobertura (2.200+); datos premium (xG, expected lineups, coordenadas);
  **empresa UE** (mejor encaje RGPD/legal).
- **Inconvenientes:** **más caro** y **planes por nº de ligas** (5/30/120) → multi-liga
  encarece; overkill para el MVP.

### Opción C — Football-Data.org
- **Ventajas:** free/barato; simple; bueno para prototipar y como redundancia de fixtures.
- **Inconvenientes:** **sin datos de jugador** (alineaciones/subs/tarjetas) en free; 12
  competiciones; marcadores retrasados. **Insuficiente como fuente única.**

### Opción D — Enterprise (Opta/Stats Perform, Sportradar)
- **Ventajas:** datos oficiales licenciados, máxima calidad.
- **Inconvenientes:** contratos enterprise caros; inviable en bootstrapping.

## Decisión

**Estrategia de proveedor por fases** (presupuesto de desarrollo = €0):

1. **Durante todo el desarrollo y el testing → proveedor `mock` propio y gratuito.**
   Primer adaptador del Data Hub: **seed realista** (liga/equipos/plantillas) — liga modelada:
   **LaLiga (Primera División española)** — + **simulador de partidos y eventos** (resultados, goles, asistencias, tarjetas, minutos, alineaciones,
   cambios, lesiones, datos de entrenador). Coste €0, sin rate limits, **determinista** y con
   **casos límite a demanda** para testear los motores de puntuación, entrenadores y estadio.
2. **Al salir al mercado (hacia M5→M6) → API-Football (Opción A)**, plan **Pro (~$19/mes)**,
   como proveedor de datos **reales**. Se elige por cobertura/precio, por incluir
   **entrenadores** y porque su modelo "todas las ligas incluidas" favorece el multi-liga.
   El gasto se asume **solo cuando el producto esté listo para usuarios reales**.
3. **Ambos son adaptadores intercambiables detrás del Football Data Hub**: normalización a
   nuestro modelo con **IDs internos**; ningún componente aguas abajo conoce al proveedor.
   Pasar de `mock` a API-Football = **implementar un adaptador nuevo**, sin tocar backend ni
   frontend. (El mock, además, valida la arquitectura del Hub desde el día 1.)
4. **Alternativas documentadas:** **SportMonks** como *upgrade* (calidad/xG, empresa UE);
   **Football-Data.org** como posible **redundancia** de fixtures/standings, y como posible
   fuente **gratuita de una sola vez** para sembrar datos reales en el mock.
5. **Postura legal (de [`../research/Legal.md`](../research/Legal.md)):** usar **nombres +
   estadísticas**; **evitar fotos reales, escudos, camisetas y logos** (arte generado);
   revisión legal antes de producción (M6). No bloquea desarrollo ni beta cerrada.

## Consecuencias

- **Positivas:** **desarrollo a coste €0**; sin rate limits ni claves durante la
  construcción; datos **deterministas** y **casos límite a demanda** → mejores tests; el mock
  **valida la arquitectura del Data Hub desde el día 1**; el gasto en API real se difiere a
  cuando aporta valor (usuarios reales); riesgo legal mayor (imágenes) esquivado por diseño.
- **Negativas / coste asumido:** hay que **construir y mantener** el mock (seed + simulador),
  aunque su valor para testing lo compensa; los datos simulados **no son la realidad** (hay
  que integrar el adaptador real antes de la beta, ~Sprint 16); dependeremos entonces de la
  calidad/uptime de API-Football (mitigado por el Data Hub).
- **Impacto:** habilita el Sprint 1 (modelo de dominio) y Sprints 2-3 (adaptador `mock` +
  simulador). El diseño del adaptador/sync se detalla en el **ADR-005**. La integración del
  adaptador real (API-Football) se planifica hacia el **Sprint 16** (pre-beta).

## Notas / seguimiento

- Verificar el **ToS de uso comercial/redistribución** de API-Football antes del lanzamiento público.
- Reevaluar proveedor si: (a) la calidad de datos de entrenadores resulta insuficiente para
  el algoritmo (Sprint 11), o (b) el coste de infra de sync se dispara.
- Este ADR **no** compromete la arquitectura del sync (ADR-005) ni el modelo de datos (ADR-006).
