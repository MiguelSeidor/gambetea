# ADR-004 — Estructura de repositorio (monorepo)

- **Estado:** Aceptado  *(ratificado por el propietario, 2026-07-27)*
- **Fecha:** 2026-07-27
- **Decisores:** CTO (propuesta) · Propietario (ratifica)
- **Fase:** 0 (Investigación)

## Contexto

Tenemos ya una app **Next.js** (`web/`) y añadiremos una API **NestJS** (ADR-002). Ambas
comparten **contratos**: el modelo de dominio (IDs internos), la **interfaz del proveedor**
(ADR-001), DTOs de la API y tipos. Queremos evitar duplicar tipos entre front y back, y que
todo evolucione de forma coherente. Despliegue: Railway (por servicio, **sin Docker**).

## Opciones consideradas

### Opción A — Monorepo (pnpm workspaces + Turborepo)
- **Ventajas:** un solo repo; **paquetes compartidos** (tipos/contratos) sin publicar nada;
  refactors atómicos front+back; tooling y config compartidos; Turborepo cachea/orquesta
  tareas (gratis). pnpm: rápido y eficiente en disco, pensado para workspaces.
- **Inconvenientes:** un poco de setup inicial; hay que **migrar `web/` de npm a pnpm**.

### Opción B — Dos repos separados (web / api)
- **Ventajas:** aislamiento total.
- **Inconvenientes:** compartir contratos obliga a **duplicar** o a publicar un paquete
  (overhead); refactors cruzados dolorosos. Mal encaje para un dev en solitario.

### Opción C — Monorepo con Nx
- **Ventajas:** muy potente para Nest+Next, generadores.
- **Inconvenientes:** más pesado/opinado de lo que necesitamos ahora.

## Decisión

**Monorepo con pnpm workspaces + Turborepo (Opción A).** Estructura objetivo:

```
gambetea/                 (raíz del repo actual)
├── apps/
│   ├── web/              (Next.js — mover el actual web/ aquí)
│   └── api/              (NestJS)
├── packages/
│   ├── domain/           (tipos e interfaces del dominio, contrato del proveedor, DTOs)
│   └── config/           (tsconfig, eslint, prettier compartidos)
├── docs/  adr/  research/  brand/   (ya existentes)
├── package.json          (workspaces)  ·  pnpm-workspace.yaml  ·  turbo.json
```

- **`packages/domain`** es la fuente única de contratos compartidos (lo consumen web y api).
  El **cliente Prisma no** vive aquí (se queda en `apps/api`, ADR-003).
- **Railway**: un servicio por app, con *root directory* y build por servicio (Nixpacks, sin
  Docker).
- Gestor de paquetes: **pnpm** (más eficiente para monorepos que npm).

## Consecuencias

- **Positivas:** cero duplicación de tipos; DX de refactor cruzada; base preparada para
  añadir más apps/paquetes (p. ej. `packages/ui`) sin reestructurar.
- **Negativas / coste asumido:** setup del workspace y **migración de `web/` a pnpm** (coste
  bajo, se hace ahora que es pronto).
- **Impacto:** primera tarea del Sprint 0 (tooling). Condiciona dónde vive el schema Prisma
  (`apps/api`) y los contratos (`packages/domain`).

## Notas / seguimiento

- Si en el futuro el monorepo se complica, valorar Nx.
- Verificar el flujo de despliegue de monorepo en Railway por servicio.
