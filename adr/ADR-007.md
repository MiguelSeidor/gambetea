# ADR-007 — Diseño de la API (REST vs GraphQL)

- **Estado:** Aceptado  *(ratificado por el propietario)*
- **Fecha:** 2026-07-28
- **Decisores:** CTO (propuesta) · Propietario (ratifica)
- **Fase:** 4 (Backend) · Sprint 4

## Contexto

El frontend (Next.js) consume la API del backend (NestJS, ADR-002). Hay que decidir el
**estilo de API**: REST o GraphQL. Nuestras necesidades son CRUD/acciones bastante directas
(auth, ligas, plantilla, alineación, mercado, puntuación).

## Opciones consideradas

### A — REST (JSON) con NestJS
- **Ventajas:** simple y universal; encaja de serie con los controladores de NestJS; fácil de
  cachear, versionar, testear (lo acabamos de verificar con curl/health/auth); menos tooling.
- **Inconvenientes:** over/under-fetching en pantallas complejas (mitigable con endpoints a
  medida); sin schema tipado autogenerado (mitigable con OpenAPI/Swagger + tipos compartidos).

### B — GraphQL
- **Ventajas:** el cliente pide justo lo que necesita; schema tipado.
- **Inconvenientes:** complejidad (resolvers, N+1, caché, seguridad de queries) **no
  justificada** para nuestro alcance actual; más superficie que mantener en solitario.

## Decisión

**REST/JSON con NestJS (Opción A).** Convenciones:
- Prefijo global **`/api`**. Versionado futuro con `/api/v1` si hiciera falta.
- **Autenticación JWT Bearer** (`Authorization: Bearer <token>`), guard de Passport.
- **Validación** de entrada con `class-validator` + `ValidationPipe` global (`whitelist`).
- Errores con los códigos HTTP estándar (400/401/409/…).
- Documentación futura con **OpenAPI/Swagger** (`@nestjs/swagger`) cuando crezca la API.

GraphQL queda descartado por ahora; podría añadirse más adelante como capa opcional si un
cliente lo requiere, sin romper REST.

## Consecuencias

- **Positivas:** velocidad de desarrollo, testeo simple, menos piezas móviles; base ya
  probada (auth de extremo a extremo funcionando).
- **Negativas / coste asumido:** endpoints a medida para pantallas ricas; mantener tipos
  compartidos front/back a mano (o vía OpenAPI) — candidato a `packages/domain`.
- **Impacto:** define el estilo de todos los módulos siguientes (ligas, plantilla, mercado…).

## Notas / seguimiento

- Añadir Swagger cuando haya varios módulos de dominio.
- Evaluar generar tipos del cliente a partir de OpenAPI para no duplicar contratos.
