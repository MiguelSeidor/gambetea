# ADR-016 — Rol de administrador global + panel de overrides (god-mode del Hub)

- **Estado:** Propuesto  *(pendiente de ratificación del propietario)*
- **Fecha:** 2026-07-30
- **Decisores:** CTO (propuesta) · Propietario (ratifica)
- **Fase:** 8+ · Sprint 17 (Fase 4 de "plataforma configurable")

## Contexto

El Football Data Hub sincroniza datos de un proveedor externo que **fallará** (goles mal
asignados, alineaciones erróneas, valores raros, un fichaje que debe deshacerse…). El
propietario quiere una **cuenta y rol de administrador GLOBAL** capaz de corregir casi todo a
mano: deshacer/rehacer fichajes, cambiar valores de mercado, editar/añadir/quitar jugadores y
entrenadores, dar/quitar dinero y corregir puntuaciones.

Es god-mode: por definición salta las reglas de negocio. Necesita **autorización estricta** y
**traza de auditoría** (quién hizo qué y cuándo), porque puede alterar la economía y la
clasificación de cualquier liga.

## Decisión

### 1. Autorización — rol global, separado del rol por liga

Los roles actuales son **por liga** (`LeagueMembership.role`: OWNER/MEMBER). El admin es
**global**, así que va en el usuario: **`User.isAdmin`** (boolean). El JWT sigue igual (sólo
`sub`); `JwtStrategy` ya carga el usuario, así que expone `isAdmin` en el request. Un
**`AdminGuard`** (tras `JwtAuthGuard`) exige `isAdmin` → 403 si no.

Bootstrap: un usuario se promueve con el script [`scripts/make-admin.mjs`](../apps/api/scripts/make-admin.mjs)
(`<email>`). No hay auto-registro de admin (no se expone endpoint para ello).

### 2. Auditoría — toda acción admin queda registrada

**`AdminAction`** (id, `adminId`, `action`, `target`, `detail JSON`, `createdAt`). Cada override
escribe una fila **antes/junto** al cambio. Es la red de seguridad de un god-mode y la base para
"deshacer" con criterio.

### 3. Overrides (módulo `/admin`, todos con `AdminGuard` + auditoría)

| Acción | Endpoint | Efecto |
|---|---|---|
| Panorama | `GET /admin/overview` | ligas, equipos y jornadas (selectores del panel) |
| Detalle de equipo | `GET /admin/teams/:id` | saldo, plantilla (jug/entr con valor), últimas transacciones |
| Dar/quitar dinero | `POST /admin/teams/:id/money` | `budget += amount` + `Transaction ADJUST` |
| Editar jugador | `PATCH /admin/players/:id` | nombre, posición, club, **rating**, **valor** |
| Crear jugador | `POST /admin/players` | alta en un club real |
| Borrar jugador | `DELETE /admin/players/:id` | sólo si no está en ninguna plantilla |
| Editar entrenador | `PATCH /admin/coaches/:id` | nombre, valor |
| Reasignar / deshacer fichaje | `POST /admin/leagues/:id/reassign` | mueve `RosterPlayer` de un equipo a otro (con ajuste opcional de caja) |
| Corregir puntuación de equipo | `POST /admin/fantasy-score` | fija `FantasyGameweekScore.points` de una jornada |
| Recalcular jornada | `POST /admin/gameweeks/:id/recompute` | re-ejecuta el scoring (tras corregir datos del Hub) |
| Auditoría | `GET /admin/audit` | últimas acciones admin |

**Principios:**
- Los overrides **no** disparan efectos en cascada de negocio (no repagan primas, no relanzan
  mercado): son correcciones quirúrgicas. Para recalcular puntos tras tocar datos, existe
  `recompute` explícito.
- El dinero se mueve **siempre** con una `Transaction` (rastro económico coherente).
- "Cambiar valor de mercado" toca `Player.value`/`Coach.value` directamente; el siguiente
  recálculo de valores (mercado 00:00) puede volver a moverlo salvo que también se ajuste el
  `rating` (que es la base). El panel deja editar ambos.

### 4. Web — panel `/admin` sólo visible para admins

Página con las acciones de arriba (ajuste de caja, edición de jugador, reasignación, corrección
de puntos, recálculo, auditoría). El item de menú y la ruta se ocultan si `!user.isAdmin`
(defensa en cliente; la real es el `AdminGuard` del backend).

## Opciones consideradas

- **A — `User.isAdmin` boolean (elegida).** Mínimo y claro; un único nivel global. Suficiente hoy.
- **B — Enum `User.role` (USER/ADMIN/SUPPORT…).** Prepara niveles/permisos finos; prematuro, se
  puede migrar desde el boolean cuando haga falta.
- **C — Reusar `LeagueMembership.role`.** Descartada: el admin es global, no por liga; mezclar
  ámbitos confunde y no cubre datos globales del Hub (jugadores/entrenadores).

## Consecuencias

- **Positivas:** operabilidad real ante fallos del proveedor sin tocar la BD a mano; traza de
  auditoría; base para automatizar correcciones recurrentes más adelante.
- **Negativas / coste asumido:** god-mode = poder de romper la economía/clasificación; se mitiga
  con auditoría y con que cada cambio de caja deje `Transaction`. Sin flujo de "deshacer"
  automático de la auditoría (v1): el admin revierte manualmente guiándose por el log.
- **Impacto:** `User.isAdmin`, `AdminAction`, `JwtStrategy`/`AuthUser` (expone `isAdmin`),
  `AdminGuard`, módulo `admin`, y el panel web `/admin`.

## Notas / seguimiento

- Evolución: "deshacer" one-click desde la auditoría; permisos finos (opción B); 2FA para admin.
- Si el equipo de soporte crece, mover a RBAC real (roles + permisos).
